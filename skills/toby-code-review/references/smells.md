# Design Smells

This is the design-smell catalog toby-code-review checks a diff against. A match becomes a finding under that skill's proof rule for smells: the entry name, the file:line, and the code there that meets the entry's Fires-when criterion. Every entry's exception makes a review here match what toby-swd-modules, toby-swd-clarity, or toby-swd-interfaces would call fine if an agent had just written this code. The judgment doesn't drift between write time and review time. Nothing below depends on those skills being loaded, so this file stands alone.

## Design smells

Entries tagged *(diff-visible)* are provable from the file list and the diff hunks alone, including any function body the diff adds or changes. Untagged entries need a cross-file search, code the diff didn't touch, or repo history to prove.

- **Long parameter list / data clump** *(diff-visible)* — a signature carries enough parameters, or the same small group of parameters keeps recurring together across signatures, that grouping them into one object would simplify every call site. **Fires when** a changed or new signature has enough parameters that a caller has to check the declaration to get the order right, or the same 2-3 parameters — a range, a coordinate pair, an address triple — show up together in multiple signatures in the diff. **Exception** — a signature where each parameter is independently necessary, with named or keyword arguments keeping the call site readable, is fine. Flag it only when grouping would cut what a caller has to track to call it correctly. The parameter count by itself proves nothing. Route to toby-swd-interfaces.

- **Output argument** *(diff-visible)* — a function's result comes back through a mutated parameter: a field set on a passed-in object, a value pushed into a passed-in array. Callers have to read the body to find the write. **Fires when** the diff adds or changes a function that writes into a received parameter as its way of producing a result, where a return value could carry the same information. **Exception** — output parameters are the idiom for `(result, err)`-style returns, a documented caller-provided buffer used for performance, or a method whose whole declared job is mutating the receiver it was called on. Those pass. Route to toby-swd-interfaces.

- **Flag / selector argument** *(diff-visible)* — a boolean or enum parameter picks which of two different behaviors a function runs. **Fires when** a changed or new function branches on a boolean or enum parameter near the top of its body into substantially different code paths, and the parameter's only job is choosing which path runs. **Exception** — a parameter that selects among values within one coherent operation is fine. toby-swd-interfaces' one-method-per-caller-shape red flag argues for consolidating those into a single method with a value or query parameter. A parameter picking a value the operation acts on passes. A parameter picking which operation runs is the smell. Route to toby-swd-interfaces.

- **Accessors as the public surface** — an interface built mostly from per-field get/set methods exposes the data layout with extra syntax, the same shape as the implementation it's supposed to hide. **Fires when** a new or changed class or module's public methods are mostly getters and setters for its own fields, with no operations that name intent. **Exception** — a record kept deliberately as plain data, with its behavior owned by another module, is fine. There the data is the contract and the depth lives in the module that owns the behavior. Route to toby-swd-interfaces.

- **Message chain** *(diff-visible)* — a caller reaches through several objects to get what it needs — `a.getB().getC().getD().getValue()` — coupling itself to the whole intermediate structure. **Fires when** a changed line chains three or more navigations through different objects' accessors to reach a final value or call. **Exception** — a fluent builder or a functional pipeline (`.map().filter().reduce()`, a query builder), where each call returns a new value of the same conceptual type, is fine. Route to toby-swd-interfaces.

- **Pass-through method** *(diff-visible)* — a method whose body is a single call to another method, forwarding the same arguments with no added logic. **Fires when** a new or changed method's body does exactly that: one call through, same signature shape, nothing added. **Exception** — a layer with a real near-future need for a stable entry point is fine. Name the concrete near-future use, or it's speculative. Implementing a shared interface doesn't excuse it on its own. toby-swd-modules calls a decorator that adds little a shallow pass-through in disguise, worth questioning even when it satisfies a contract. Route to toby-swd-modules.

- **Speculative generality** — a parameter, hook, or extension point added for a future that has no named caller yet. **Fires when** a new parameter, config option, or extension point has no current caller using anything but its default, and no concretely named near-future use. **Exception** — an interface covering today's needs plus one or two named near-future variants is fine. Some generality is the target. The line is whether a real use can be named. Route to toby-swd-interfaces.

- **Artificial coupling** *(diff-visible)* — a constant, utility function, or type dropped inside a class or module it has no substantive relationship to, because that's where it was convenient to put it. **Fires when** the diff adds a general-purpose constant or helper inside a specific, unrelated class or module, and nothing about that class's own job explains why it owns this. **Exception** — placement where the two things share real knowledge (passes toby-swd-modules' decompose-by-knowledge test), or placement that follows an established repo convention, is fine. Route to toby-swd-modules.

- **Feature envy** — a method that reads and calls another object's data or methods more than its own, doing that object's job from inside the wrong boundary. **Fires when** a method's body is mostly a chain of getters or fields pulled from one other object, with little use of its own class's state, and that other object could reasonably own the operation. **Exception** — a method whose whole declared job is combining or comparing data across objects — a comparator, mapper, reducer, aggregator — is fine. Reading several objects is the design. Route to toby-swd-modules.

- **Shallow module** — the interface costs almost as much to learn as the implementation behind it would cost to inline at the call site. **Fires when** a new or changed module's public surface — parameters, methods, required setup — takes about as much explaining as its internals would. **Exception** — small utilities are sometimes unavoidably shallow, and that's fine. Don't inflate a trivial helper into artificial depth to dodge the label. Route to toby-swd-modules.

- **Information leakage** — one hidden design decision — a file format, wire protocol, storage layout, policy — shows up in more than one module, so changing the decision means changing all of them. **Fires when** the diff touches two or more modules to express what is really one decision: the same knowledge duplicated across them when it should live in exactly one place. **Exception** — a dispatcher and the handlers it selects between, several implementations of one interface, a decorator and the object it wraps, or an interface known to both caller and implementer are fine. Each contributes distinct functionality despite the shared shape. Two blocks that share text while answering to different reasons to change are also fine, however identical they look. Merging them couples decisions that should move apart, and the next change tears them back out. Ask what would make each one change. Separate answers mean separate code. Route to toby-swd-modules.

- **Duplicated knowledge** *(diff-visible)* — one rule or decision written out in two or more places, so a change to it has to land in all of them or they drift apart. Covers a single file, where information leakage's two-module trigger never fires. **Fires when** two or more blocks encode the same decision — the same validation rule, the same format, the same threshold — and you can state the one reason that would change every copy together. **Exception** — blocks that share text while answering to different reasons to change stay separate, however identical they look. Ask what would make each one change. Separate answers mean separate code, and merging them couples decisions that should move apart. Route to toby-swd-clarity.

- **Divergent change** *(diff-visible)* — one class or module gets modified for many unrelated reasons in the same change, a sign it carries more than one piece of knowledge. **Fires when** the diff's stated intent is one change, but the edits inside a single file or class serve visibly unrelated purposes — a pricing-rule tweak and a display-copy tweak landing in the same class in the same commit. **Exception** — a class with one cohesive responsibility that legitimately needs many small methods, like a serializer with one method per field type, is fine. The tell is whether the edits are driven by unrelated business reasons. A high method count by itself proves nothing. Route to toby-swd-modules.

- **Shotgun surgery** *(diff-visible)* — one conceptual change forces small edits scattered across many files or classes, the diff-visible symptom of information leakage running in reverse. **Fires when** the diff touches many files with small, similar-shaped edits — a field added to N structs, a case added to N switch statements — that all encode the same underlying decision. **Exception** — N edits that are independent facts which happen to co-occur, like a changelog entry, a version bump, and a config update landing in one PR, are fine. That's bookkeeping. The tell: if the decision changed again, would all N have to change again the same way? Route to toby-swd-modules.

- **Primitive obsession** — a domain concept — money, a phone number, a date range, a role code — represented as a bare string, int, or float, with parsing or validation for that concept duplicated at each use site. **Fires when** a new field or parameter representing a recognizable domain concept is typed as a raw primitive, and the same parsing, validation, or formatting for that concept already appears at 2+ other call sites. **Exception** — a primitive used in exactly one place, with no duplicated logic elsewhere, is fine. Wrapping a single unremarkable string in a type is speculative generality run in reverse. Route to toby-swd-interfaces.

- **Magic number or string** *(diff-visible)* — an unexplained literal doing real work in the logic, standing in for a named concept. **Fires when** a changed line compares against, multiplies by, or branches on a bare literal with no obvious meaning nearby, or the same literal repeats at 2+ sites for one concept. **Exception** — a self-evident value in a narrow, obvious scope is fine — a loop's 0/1/-1, an HTTP status checked once inline. The tell is a value with no obvious meaning, or repetition across sites where a change to one should change all. A literal you quoted while proving another finding still counts here. Route to toby-swd-clarity.

- **Mixed levels of abstraction in one function** *(diff-visible)* — a function's body swings between calling well-named subordinate operations and doing raw low-level work for the same conceptual step, forcing the reader to switch altitude mid-block. **Fires when** within one function in the diff, some statements read as named steps of a plan and others are inlined mechanics that could just as easily be a named step. **Exception** — a function that's uniformly low-level throughout — a tight numeric loop, a parser — is fine. Per toby-swd-modules, a long method that's one coherent deep abstraction with a simple signature is fine too. The smell is uneven altitude within one function. Length by itself proves nothing.

- **Stale comment beside changed code** *(diff-visible)* — a comment sitting right next to code the diff just changed still describes the old behavior, type, or condition. **Fires when** the diff changes what a line or block does, and the comment immediately above or beside it — visible in the same hunk — still describes the pre-change behavior. **Exception** — a comment describing something that didn't change, like an invariant that still holds or a unit that's still correct, is fine. Flag it only when the diff visibly alters the exact thing the adjacent comment asserts.

- **Comment invalidated at a distance** — a change makes a comment elsewhere in the codebase, away from the edit itself, factually wrong: a caller's documented assumption, an invariant description at a distant call site, a doc comment describing behavior that just changed. **Fires when** the diff changes a function's behavior, return shape, error conditions, or an invariant, and a comment elsewhere — found by searching for callers or the described behavior — still asserts the old behavior. **Exception** — a hunch that something elsewhere might describe this doesn't clear the bar. Only flag it with the specific file:line and a quote of why the diff makes it false.

- **Dead function or class** — a function, method, or class that compiles and could run, but nothing in the system calls it anymore. **Fires when** the diff removes the last caller of a function or class, or a repo-wide search for the symbol's name turns up only its own definition. **Exception** — anything exported or public that consumers outside this repo might use, or anything reached through reflection, dependency injection, dynamic dispatch, or a test-only harness, is fine. Grep for the identifier as a string and confirm export and visibility status before flagging.
