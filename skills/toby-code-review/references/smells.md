# Design Smells

For each entry, check the Exception as closely as the Fires when line, because code that matches an Exception is fine. An entry tagged *(diff-visible)* can be proved from the diff alone. For an untagged entry, quote the search you ran or the unchanged code that proves it.

- **Long parameter list / data clump** *(diff-visible)*. **Fires when** a changed or new signature has so many parameters that a caller has to check the declaration to get the order right. This entry also applies when the diff has the same 2 or 3 parameters together in more than one signature, such as a range, a coordinate pair, or an address triple. **Exception.** A signature is fine when each parameter is needed on its own and named or keyword arguments keep the call site readable. Report it only when grouping the parameters would leave a caller fewer things to get right. The parameter count by itself proves nothing. **Fix.** Group the parameters that are always passed together into one object or value type, and pass that.

- **Output argument** *(diff-visible)*. A function returns its result by changing a parameter, such as setting a field on an object passed in or pushing a value into an array passed in. Callers have to read the body to find the write. **Fires when** the diff adds or changes a function that produces its result by writing into a parameter it received, and a return value could hold that information. **Exception.** Output parameters are fine when they are the usual way to return a result and an error together, as in `(result, err)`-style returns. A documented buffer that the caller provides for speed is also fine. So is a method whose whole documented purpose is to change the object it is called on, and a method that changes state as its normal job. **Fix.** Return the result, and leave the caller's argument unchanged.

- **Flag / selector argument** *(diff-visible)*. A boolean or enum parameter picks which of two different behaviors a function runs. **Fires when** a changed or new function branches near the top of its body on a boolean or enum parameter into very different code paths. This entry applies only when choosing which path runs is the parameter's only job. **Exception.** A parameter that picks a value the operation acts on is fine. This smell is about a parameter that picks which operation runs. **Fix.** Split the function into one function per behavior, each named for what it does. Each caller then calls the one it needs.

- **Repeated type switch** *(diff-visible)*. A `switch` or `if`/`else if` chain branches on a type tag, a `kind` or `type` field, an enum, a role, or a status, and each branch runs different behavior. The diff adds a branch to that chain or adds a second chain over the same tag. Each new type or status added later needs an edit to this code. When two chains branch on the same field, one gets updated and the other gets missed. **Fires when** a diff hunk adds a `case` or branch to an existing conditional that branches on a tag. This entry also applies when a hunk adds a conditional on a field that another conditional in the changed files already branches on. **Exception.** One exhaustive `switch` over a closed discriminated union, guarded by a `never` or unreachable check, is fine. A single lookup map that picks the behavior is also fine. **Fix.** Put the code that picks the behavior for each case in one place, so adding a case edits one place. Use a lookup map for small cases, or one implementation per case when each case has its own state.

- **Getters and setters as the whole interface**. An interface made mostly of a get and a set method for each field shows callers the data layout with extra syntax. A caller has to understand the interface as well as they would understand the implementation it is meant to hide. **Fires when** the public methods of a new or changed class or module are mostly getters and setters for its own fields, and no operation has a name that says what it is for. **Exception.** A record kept as plain data on purpose, with its behavior defined in another module, is fine. In that case, callers depend on the fields directly. The useful logic is in the module that defines the behavior. **Fix.** Replace the getters and setters with operations named for what callers need done, and keep the fields private.

- **Message chain** *(diff-visible)*. A caller goes through several objects to get what it needs, as in `a.getB().getC().getD().getValue()`. The caller then depends on every object in between. **Fires when** a changed line chains three or more calls through different objects' accessors to reach a final value or call. **Exception.** A fluent builder or a functional pipeline is fine, such as `.map().filter().reduce()` or a query builder, where each call returns a new value of the same kind. **Fix.** Add a method on the first object that returns what the caller needs, so the caller no longer goes through the objects in between.

- **Pass-through method** *(diff-visible)*. A method's body is a single call to another method that passes on the same arguments and adds no logic. **Fires when** a new or changed method's body is one call to another method with the same signature and nothing added. **Exception.** A layer is fine when a real near-future need requires a stable entry point. State that near-future use. If you cannot state it, the layer is speculative and the exception does not apply. Implementing a shared interface is not enough by itself to make the method an exception. **Fix.** Delete the forwarding method and call the lower method directly, or move real work into the layer so the layer adds something.

- **Speculative generality**. Someone added a parameter, hook, or extension point for a future use that has no known caller yet. **Fires when** no current caller passes anything but the default to a new parameter, config option, or extension point, and nobody has named a concrete near-future use. **Exception.** An interface that covers today's needs plus one or two named near-future variants is fine. The test is whether someone can point to a real use. **Fix.** Remove the parameter or extension point until a caller needs it, and set the value inside the module.

- **Artificial coupling** *(diff-visible)*. Someone put a constant, utility function, or type inside a class or module that has no real relationship to it, because that placement was convenient. **Fires when** the diff adds a general-purpose constant or helper inside a specific, unrelated class or module. This entry applies only when that class's own job does not explain why the constant or helper is there. **Exception.** The placement is fine when the constant or helper is part of the rule that the module implements. It is also fine when it follows a convention the repo already uses. **Fix.** Move the constant or helper to the module whose job uses it, or to a small shared module for general helpers.

- **Feature envy**. A method reads another object's data and calls that object's methods more than its own, so the method does that object's job from the wrong class. **Fires when** a method's body is mostly getters or fields taken from one other object, with little use of its own class's state. This entry applies only when the operation could reasonably be a method of that other object. **Exception.** A method whose whole documented purpose is to combine or compare data across objects is fine, such as a comparator, mapper, reducer, or aggregator. Those methods are meant to read several objects. **Fix.** Move the method onto the object whose data it reads.

- **Shallow module**. Learning the module's interface takes almost as much effort as writing its implementation directly at the call site. **Fires when** a new or changed module's parameters, methods, and required setup take about as much explaining as the code inside it would. **Exception.** Some small utilities cannot avoid being shallow, and that is fine. Do not add extra layers to a small helper only to avoid this label. **Fix.** Merge the module into its caller, or move more of the work behind its interface so callers have less to manage.

- **Fat interface** *(diff-visible)*. An interface or abstract type has methods that a consumer never calls, so every implementation and every test double must still provide those methods. **Fires when** the diff adds a method to an existing interface, and an implementer in the diff stubs it with `throw`, `return null`, or an empty body. This entry also applies when the diff adds a consumer that receives a wide interface and calls only one or two of its methods. **Exception.** A broad interface is fine when each implementer uses all of it. A standard-library interface for one capability, such as `Iterable` or `Closeable`, is also fine. **Fix.** Split the interface so each consumer depends only on the methods it calls.

- **Information leakage**. One hidden design decision, such as a file format, wire protocol, storage layout, or policy, appears in more than one module. Changing the decision means changing all of those modules. **Fires when** the diff touches two or more modules to express one decision, so the same knowledge appears in several places when it belongs in exactly one. **Exception.** A dispatcher and the handlers it chooses between are fine. So are several implementations of one interface, and a decorator and the object it wraps. An interface known to both caller and implementer is also fine. In each of these cases, every module adds its own behavior, even though the modules share a structure. **Fix.** Put the decision in one module, and have the other modules call that module.

- **Hardwired dependency** *(diff-visible)*. A function or class doing domain or policy work creates or reads a concrete outside collaborator itself. Examples are `new PaymentClient()`, `new S3Client(...)`, a direct `process.env.X` or `import.meta.env.X` read for its own use, and an imported I/O singleton. Nobody can point that code at a different service, or test it with a fake, without editing it. **Fires when** the diff adds a constructor call inside a function or class for a type that holds network, disk, clock, or external-service state. This entry also applies to a direct environment-variable read for that code's own use. **Exception.** Creating a plain value or a pure helper is fine. Wiring belongs in `main`, a provider, a factory, a designated config module, or the composition root. The composition root is the place where the program creates and connects its main objects. Wiring also belongs in a place the framework provides for it, such as a data hook that creates its client. **Fix.** Pass the collaborator in through the constructor or a parameter, and create it in the entry point or a factory.

- **Duplicated knowledge** *(diff-visible)*. One rule or decision is written out in two or more places, so a change to it has to be made in every copy, or the copies disagree. Use this entry when the copies are in one file. Information leakage covers copies in two or more modules. **Fires when** two or more blocks express the same decision, such as a validation rule, a format, or a threshold. This entry applies only when you can also state the one reason that would change every copy together. **Exception.** Blocks that share text but have different reasons to change stay separate, however identical they look. Ask what would make each block change. When the answers differ, keep the blocks separate, because merging them ties together decisions that should change separately. **Fix.** Keep the rule in one function or constant, and replace each copy with a call to it.

- **Divergent change** *(diff-visible)*. One class or module is changed for many unrelated reasons in the same change, which suggests that the class handles more than one responsibility. **Fires when** the diff's stated purpose is one change, but the edits inside a single file or class serve visibly unrelated purposes. An example is a pricing-rule tweak and a display-copy tweak made in the same class in the same commit. **Exception.** A class with one coherent responsibility that needs many small methods is fine, such as a serializer with one method per field type. Check whether unrelated business reasons drive the edits. A high method count by itself proves nothing. Judge this smell from the diff alone, because this review does not read a file's commit history. **Fix.** Split the class along the unrelated reasons, so each piece changes for one reason.

- **Subtype breaks the base type's contract**. An override or implementation breaks a promise that callers of the base type rely on. The override throws where the base returns, refuses input the base accepts, drops a documented side effect or return value, or ignores a parameter the base uses. A caller holding the base type gets the different behavior with no warning. **Fires when** the diff adds or changes a subtype or implementation, and an overriding method throws `UnsupportedOperationException` or `NotImplementedError`, or accepts a narrower range of arguments. This entry also applies when an override returns a value the base contract does not allow, such as a nullable value where the base is non-null, or a different unit or meaning. **Exception.** A partial implementation that the type system marks as partial is fine. So is a method such as `supportsX()` that callers are expected to check first. **Fix.** Make the override follow the base contract, or stop the type from implementing that base and give it its own interface.

- **Shotgun surgery** *(diff-visible)*. One design change forces small edits scattered across many files or classes. **Fires when** the diff touches many files with small, similar edits that all express the same decision. Examples are a field added to N structs, or a case added to N switch statements. **Exception.** N edits that record independent facts are fine, even when they appear in one PR. A changelog entry, a version bump, and a config update are bookkeeping of that kind. To tell the two apart, ask whether all N edits would have to change the same way if the decision changed again. **Fix.** Put the decision that the edits repeat in one module, so the next change of this kind edits one file.

- **Primitive obsession**. A domain concept, such as money, a phone number, a date range, or a role code, is stored as a bare string, int, or float. The parsing or validation for that concept is repeated at each place that uses it. **Fires when** a new field or parameter for a recognizable domain concept is typed as a raw primitive. This entry applies only when the same parsing, validation, or formatting for that concept already appears at 2 or more other call sites. **Exception.** A primitive used in exactly one place, with no repeated logic elsewhere, is fine. Wrapping a single ordinary string in a type is also a form of speculative generality. **Fix.** Add a small type for the concept, with its parsing and validation in one place, and use it at each site.

- **Magic number or string** *(diff-visible)*. An unexplained literal affects the logic and stands for an idea that should have a name. **Fires when** a changed line compares against, multiplies by, or branches on a bare literal with no explanation nearby. This entry also applies when the same literal repeats at 2 or more sites for one idea. **Exception.** A value whose meaning anyone can see in a small scope is fine, such as a loop's 0, 1, or -1, or an HTTP status checked once inline. Report a value with no obvious meaning, or a value repeated across sites where changing one should change all of them. If you already quoted a literal as evidence for another finding, still report it here. **Fix.** Give the literal a named constant, defined once, and use the name at each site.

- **Mixed levels of abstraction in one function** *(diff-visible)*. A function's body mixes calls to well-named lower-level operations with raw low-level work for the same step. The reader has to switch between levels of detail in the middle of a block. **Fires when** some statements in one function in the diff read as named steps of a plan, and other statements in that function are low-level code written out in place. That low-level code could as easily be a named step. **Exception.** A function that is low-level all the way through is fine, such as a tight numeric loop or a parser. A long method that does one coherent job behind a simple signature is also fine, as toby-swd-modules describes. This smell is about uneven levels of detail within one function. Length by itself proves nothing. **Fix.** Move the low-level code into a named step at the same level as the steps around it.

- **Stale comment beside changed code** *(diff-visible)*. A comment right next to code the diff changed still describes the old behavior, type, or condition. **Fires when** the diff changes what a line or block does, and the comment directly above or beside it in the same hunk still describes the old behavior. **Exception.** A comment about something that did not change is fine, such as an invariant that still holds or a unit that is still correct. Report it only when the diff visibly changes the exact thing the comment next to it states. **Fix.** Rewrite the comment to state what the code does now.

- **Comment invalidated at a distance**. A change makes a comment elsewhere in the codebase false. The comment can be a caller's documented assumption, a description of an invariant at a distant call site, or a doc comment for behavior that just changed. **Fires when** the diff changes a function's behavior, return type, error conditions, or an invariant, and a comment elsewhere still states the old behavior. Find that comment by searching for callers or for the described behavior. Report it only with the file:line, the quoted comment, and one sentence on how the diff makes it false. **Exception.** A comment you only suspect describes this behavior is not enough to report. **Fix.** Correct the comment at that file:line to state the new behavior.

- **Dead function or class**. A function, method, or class compiles and could run, but nothing in the system calls it anymore. **Fires when** the diff removes the last caller of a function or class, or a repo-wide search for the symbol's name finds only its own definition. Before you report it, grep for the identifier as a string and check whether the symbol is exported or public. **Exception.** Anything exported or public that code outside this repo might use is fine. So is anything reached through reflection, dependency injection, dynamic dispatch, or a test-only harness. **Fix.** Delete it.
