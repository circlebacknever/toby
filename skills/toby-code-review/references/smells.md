# Design Smells

This file is the design-smell catalog toby-code-review checks a diff against. A match becomes a finding under that skill's proof rule for smells. That rule requires the entry name, the file:line, and the code there that meets the entry's Fires-when criterion. Each entry's exception covers the same code that an agent may write under toby-swd-modules, toby-swd-clarity, or toby-swd-interfaces. As a result, code judged fine at write time is also judged fine at review time. Nothing below depends on those skills being loaded.

## Design smells

Entries tagged *(diff-visible)* are provable from the file list and the diff hunks alone, including any function body the diff adds or changes. Untagged entries need a cross-file search, code the diff didn't touch, or repo history to prove.

- **Long parameter list / data clump** *(diff-visible)* — grouping parameters into one object would simplify every call site. That happens when a signature has many parameters, or when the same small group of parameters recurs together across signatures. **Fires when** a changed or new signature has enough parameters that a caller has to check the declaration to get the order right. It also fires when the diff has the same 2-3 parameters, such as a range, a coordinate pair, or an address triple, together in more than one signature. **Exception** — a signature where each parameter is independently necessary, with named or keyword arguments keeping the call site readable, is fine. Flag it only when grouping would cut what a caller has to track to call it correctly. The parameter count by itself proves nothing. Route to toby-swd-interfaces.

- **Output argument** *(diff-visible)* — a function's result comes back through a mutated parameter: a field set on a passed-in object, a value pushed into a passed-in array. Callers have to read the body to find the write. **Fires when** the diff adds or changes a function that produces its result by writing into a received parameter, and a return value could hold that information. **Exception** — output parameters are the idiom for `(result, err)`-style returns and for a documented caller-provided buffer used for performance. A method whose whole declared job is mutating its receiver also passes, and so does ordinary state-changing behavior. Route to toby-swd-interfaces.

- **Flag / selector argument** *(diff-visible)* — a boolean or enum parameter picks which of two different behaviors a function runs. **Fires when** a changed or new function branches near the top of its body on a boolean or enum parameter into substantially different code paths. It fires only when the parameter's only job is choosing which path runs. **Exception** — a parameter that selects among values within one coherent operation is fine. toby-swd-interfaces treats one method per caller variation as a problem. That skill tells the agent to write a single method with a value or query parameter. A parameter that picks a value for the operation passes, because the smell is only a parameter that picks which operation runs. Route to toby-swd-interfaces.

- **Repeated type switch** *(diff-visible)* — a `switch` or `if`/`else if` chain branches on a type tag, `kind`/`type` field, enum, role, or status into arms that each run distinct behavior. The diff adds an arm to that chain or adds a second chain over the same tag. Every later domain case forces an edit to this code. Parallel chains also stop matching each other. **Fires when** a diff hunk adds a `case` or branch to an existing tag-dispatch conditional. It also fires when a hunk adds a conditional over a discriminant that another conditional in the changed files already switches on. **Exception** — one exhaustive `switch` over a closed discriminated union guarded by a `never` or unreachable check, or a single lookup-map dispatch, is fine. A conditional that has not gained an arm across repo history is fine. Route to toby-swd-modules.

- **Accessors as the public surface** — an interface built mostly from per-field get/set methods exposes the data layout with extra syntax. It costs a caller as much as the implementation it's supposed to hide. **Fires when** a new or changed class or module's public methods are mostly getters and setters for its own fields, with no operations whose names state what they are for. **Exception** — a record kept deliberately as plain data, with its behavior defined in another module, is fine. In that case the data is the contract. The depth is in the module that defines the behavior. Route to toby-swd-interfaces.

- **Message chain** *(diff-visible)* — a caller navigates through several objects to get what it needs, as in `a.getB().getC().getD().getValue()`, which couples the caller to the whole intermediate structure. **Fires when** a changed line chains three or more navigations through different objects' accessors to reach a final value or call. **Exception** — a fluent builder or a functional pipeline (`.map().filter().reduce()`, a query builder), where each call returns a new value of the same conceptual type, is fine. Route to toby-swd-interfaces.

- **Pass-through method** *(diff-visible)* — a method's body is a single call to another method that forwards the same arguments with no added logic. **Fires when** a new or changed method's body is one call to another method with the same signature and nothing added. **Exception** — a layer with a real near-future need for a stable entry point is fine. Name the concrete near-future use, or the layer is speculative. Implementing a shared interface doesn't excuse it on its own. toby-swd-modules describes a decorator that adds little as a shallow pass-through. Such a decorator is worth questioning even when it satisfies a contract. Route to toby-swd-modules.

- **Speculative generality** — someone added a parameter, hook, or extension point for a future that has no named caller yet. **Fires when** a new parameter, config option, or extension point has no current caller using anything but its default, and no concretely named near-future use. **Exception** — an interface covering today's needs plus one or two named near-future variants is fine. Some generality is the goal. The test is whether someone can name a real use. Route to toby-swd-interfaces.

- **Artificial coupling** *(diff-visible)* — someone put a constant, utility function, or type inside a class or module it has no substantive relationship to, because that placement was convenient. **Fires when** the diff adds a general-purpose constant or helper inside a specific, unrelated class or module. It fires only when that class's own job does not explain why the constant or helper is in it. **Exception** — placement where the two things share real knowledge (passes toby-swd-modules' decompose-by-knowledge test), or placement that follows an established repo convention, is fine. Route to toby-swd-modules.

- **Feature envy** — a method reads another object's data and calls its methods more than its own, so it does that object's job from the wrong class. **Fires when** a method's body is mostly a chain of getters or fields pulled from one other object, with little use of its own class's state. It fires only when the operation could reasonably be a method of that other object. **Exception** — a method whose whole declared job is combining or comparing data across objects, such as a comparator, mapper, reducer, or aggregator, is fine. For those methods, reading several objects is the intended design. Route to toby-swd-modules.

- **Shallow module** — the interface costs almost as much to learn as the implementation behind it would cost to inline at the call site. **Fires when** a new or changed module's parameters, methods, and required setup take about as much explaining as its internals would. **Exception** — small utilities are sometimes unavoidably shallow, and that's fine. Don't add artificial depth to a trivial helper to avoid the label. Route to toby-swd-modules.

- **Fat interface** *(diff-visible)* — an interface or abstract type has methods that a consumer never calls, so every implementation and every test double must still provide those methods. **Fires when** the diff adds a method to an existing interface, and an implementer in the diff stubs it with `throw`, `return null`, or an empty body. It also fires when the diff adds a consumer that receives a wide interface and calls only one or two of its methods. **Exception** — a broad interface whose implementers each use the whole of it, or a standard-library capability interface, is fine. Route to toby-swd-interfaces.

- **Information leakage** — one hidden design decision, such as a file format, wire protocol, storage layout, or policy, shows up in more than one module. Changing the decision means changing all of those modules. **Fires when** the diff touches two or more modules to express one decision, so the same knowledge is duplicated where it belongs in exactly one place. **Exception** — a dispatcher and the handlers it selects between, several implementations of one interface, and a decorator and the object it wraps are all fine. An interface known to both caller and implementer is also fine. Each contributes distinct functionality despite the shared structure. Two blocks that share text but have different reasons to change are also fine, however identical they look. Merging them couples decisions that should change separately. The next change then has to split them again. Ask what would make each block change, and keep the blocks separate when the answers differ. Route to toby-swd-modules.

- **Hardwired dependency** *(diff-visible)* — a unit doing domain or policy work names a concrete external collaborator itself: `new PaymentClient()`, `new S3Client(...)`, a direct `process.env.X` or `import.meta.env.X` read for its own use, an imported I/O singleton. The unit cannot be retargeted or tested without editing it. **Fires when** the diff adds a constructor call for a type holding network, disk, clock, or external-service state inside a function or class. It also fires on a direct environment-variable read for that unit's own use. Neither case counts inside an entry point, factory, or designated config module. **Exception** — constructing a plain value or a pure helper is fine. The composition root, `main`, a provider, and a factory are where wiring belongs. So is a framework-sanctioned place, such as a data hook that creates its client. Route to toby-swd-interfaces.

- **Duplicated knowledge** *(diff-visible)* — one rule or decision is written out in two or more places, so a change to it has to be made in every copy or the copies disagree. This entry covers a single file, where the two-module trigger for information leakage never fires. **Fires when** two or more blocks encode the same decision, such as a validation rule, a format, or a threshold. The entry fires only when you can also state the one reason that would change every copy together. **Exception** — blocks that share text but have different reasons to change stay separate, however identical they look. Ask what would make each block change. When the answers differ, keep the blocks separate, because merging them couples decisions that should change separately. Route to toby-swd-clarity.

- **Divergent change** *(diff-visible)* — one class or module gets modified for many unrelated reasons in the same change, which is a sign that it contains more than one piece of knowledge. **Fires when** the diff's stated intent is one change, but the edits inside a single file or class serve visibly unrelated purposes. An example is a pricing-rule tweak and a display-copy tweak made in the same class in the same commit. **Exception** — a class with one cohesive responsibility that legitimately needs many small methods, like a serializer with one method per field type, is fine. Check whether unrelated business reasons drive the edits. A high method count by itself proves nothing. Judge this smell from the diff alone, because this pass does not read a file's commit history. Route to toby-swd-modules.

- **Substitute breaks its contract** — an override or implementation contradicts what the base type's callers rely on. It throws where the base returns, refuses input the base accepts, drops a documented side effect or return value, or ignores a parameter the base uses. A caller holding the base type gets the different behavior with no warning. **Fires when** the diff adds or changes a subtype or implementation, and an overriding method throws `UnsupportedOperationException` or `NotImplementedError` or narrows an accepted argument range. It also fires when an override returns a value the base contract disallows, such as nullable where the base is non-null, or a different unit or meaning. **Exception** — a partial implementation the type system marks as partial, or a caller-visible capability check such as `supportsX()` that callers are expected to call, is fine. Route to toby-swd-clarity.

- **Shotgun surgery** *(diff-visible)* — one conceptual change forces small edits scattered across many files or classes. This pattern is the diff-visible symptom of information leakage, seen from the opposite direction. **Fires when** the diff touches many files with small, similar edits that all encode the same underlying decision. Examples are a field added to N structs, or a case added to N switch statements. **Exception** — N edits that record independent facts are fine, even when they appear in one PR. A changelog entry, a version bump, and a config update are bookkeeping of that kind. To tell the two apart, ask whether all N edits would have to change the same way if the decision changed again. Route to toby-swd-modules.

- **Primitive obsession** — a domain concept, such as money, a phone number, a date range, or a role code, is a bare string, int, or float. The parsing or validation for that concept is duplicated at each use site. **Fires when** a new field or parameter representing a recognizable domain concept is typed as a raw primitive. The entry fires only when the same parsing, validation, or formatting for that concept already appears at 2+ other call sites. **Exception** — a primitive used in exactly one place, with no duplicated logic elsewhere, is fine. Wrapping a single unremarkable string in a type is also a form of speculative generality. Route to toby-swd-interfaces.

- **Magic number or string** *(diff-visible)* — an unexplained literal affects the logic and represents a concept that should have a name. **Fires when** a changed line compares against, multiplies by, or branches on a bare literal with no obvious meaning nearby. It also fires when the same literal repeats at 2+ sites for one concept. **Exception** — a self-evident value in a narrow, obvious scope is fine, such as a loop's 0/1/-1 or an HTTP status checked once inline. Flag a value with no obvious meaning, or a value repeated across sites where a change to one should change all of them. A literal you quoted while proving another finding still counts here. Route to toby-swd-clarity.

- **Mixed levels of abstraction in one function** *(diff-visible)* — a function's body mixes calls to well-named subordinate operations with raw low-level work for the same conceptual step. The reader has to switch between levels of detail in the middle of a block. **Fires when** some statements in one function in the diff read as named steps of a plan, and other statements in that same function are inlined mechanics that could as easily be a named step. **Exception** — a function that's uniformly low-level throughout, such as a tight numeric loop or a parser, is fine. Per toby-swd-modules, a long method that's one coherent deep abstraction with a simple signature is fine too. The smell is uneven levels of detail within one function. Length by itself proves nothing.

- **Stale comment beside changed code** *(diff-visible)* — a comment right next to code the diff just changed still describes the old behavior, type, or condition. **Fires when** the diff changes what a line or block does, and the comment immediately above or beside it in the same hunk still describes the pre-change behavior. **Exception** — a comment describing something that didn't change, like an invariant that still holds or a unit that's still correct, is fine. Flag it only when the diff visibly alters the exact thing the adjacent comment asserts.

- **Comment invalidated at a distance** — a change makes a comment elsewhere in the codebase factually wrong. The comment can be a caller's documented assumption, an invariant description at a distant call site, or a doc comment for behavior that just changed. **Fires when** the diff changes a function's behavior, return type, error conditions, or an invariant, and a comment elsewhere still asserts the old behavior. Find that comment by searching for callers or for the described behavior. **Exception** — a hunch that a comment elsewhere might describe this behavior is not enough to report. Only flag it with the specific file:line and a quote of why the diff makes it false.

- **Dead function or class** — a function, method, or class compiles and could run, but the system has no remaining callers of it. **Fires when** the diff removes the last caller of a function or class, or a repo-wide search for the symbol's name turns up only its own definition. **Exception** — anything exported or public that consumers outside this repo might use is fine. So is anything reached through reflection, dependency injection, dynamic dispatch, or a test-only harness. Grep for the identifier as a string and confirm export and visibility status before flagging.
