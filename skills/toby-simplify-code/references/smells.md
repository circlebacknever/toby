# Smell Catalog

The main skill only credits a change with a literal countable reduction — fewer lines, branches, or duplicated blocks — and its Out of scope section rules out anything that moves code between modules or changes a signature. That leaves a gap: a design smell that needs a boundary fix walks past silently, because fixing it isn't this skill's job and nothing tells it to say so.

This file closes the gap. Every entry below is either:

- **Fix here** — the fix stays local and clears the countable-win bar same as anything else in What to look for. Do it in the same pass.
- **Flag, don't fix** — the fix crosses a module boundary or changes a public signature. Name the smell, the file:line, and the routing skill in the final response. Leave the code alone.

## Fix here

- **Comment invalidated at a distance.** A change makes a comment somewhere else in the codebase wrong — a caller's documented assumption, an invariant note at a distant call site, a doc comment describing behavior that just changed. Fires when the diff changes a function's behavior, return shape, error conditions, or an invariant, and a search for callers or the described behavior turns up a comment still asserting the old one. Fix here: correct the comment to match the new behavior — a one-line edit, no boundary crossed. Exception: only flag what you can name — a specific file:line and the exact clause the diff makes false. "Something elsewhere might describe this" isn't checkable. Drop it.

- **Dead function or class.** A function, method, or class that compiles and could run, but nothing calls it anymore. Fires when the diff removes its last caller, or a repo-wide grep for the symbol name turns up only its own definition. Fix here: delete it. Nothing else in the repo names it, so removing it touches no signature and no caller — pure line reduction. Exception: anything exported or public that code outside this repo might consume, and anything reached through reflection, dependency injection, dynamic dispatch, or a test-only harness. Grep the identifier as a string, confirm export status, before you delete.

- **Magic number or string.** An unexplained literal doing real work in the logic — a comparison, a multiplier, a branch condition — standing in for a concept the reader has to guess at. Fires when a changed line checks against, multiplies by, or branches on a bare literal with no obvious meaning from the surrounding lines, or the same literal shows up at two or more sites for the same concept. Fix here: name it. One constant, declared once, replaces the guesswork and the repetition. Exception: a self-evident value in a narrow scope — a loop's 0 or -1, an HTTP status checked once inline. The tell is a value nobody could explain on sight, or repetition where a change to one should change all.

- **Stale comment beside changed code.** A comment sitting right next to code the diff just changed still describes what the code used to do. Fires when a changed line or block behaves differently now, and the comment immediately above or beside it, visible in the same hunk, still asserts the old version. Fix here: rewrite the comment to match what the code does now — same hunk, roughly the same line count. Exception: a comment describing something the diff left alone — an invariant that still holds, a unit that's still correct. Flag it only when the diff visibly changes the exact thing the adjacent comment claims.

## Flag, don't fix

Each of these needs a change this skill's Out of scope note already excludes: a signature, a public return shape, or which module owns what. Name the file:line and hand it to the skill listed — that skill designs the fix; this skill only reports the smell.

### Route to toby-swd-interfaces

- **Long parameter list / data clump.** A signature carries enough parameters, or the same small group of parameters or fields keeps showing up together across several signatures, that grouping them into one object would simplify every call site. Fires when a changed or new signature has enough parameters that a caller has to check the declaration to get the order right, or the same two or three parameters — a range, a coordinate pair, an address triple — appear together more than once in the diff. Flag, don't fix: route to `toby-swd-interfaces`. Grouping the parameters changes the signature every caller uses. Exception: no fixed parameter count is a violation on its own — this repo sets no numeric ceiling. Each parameter independently necessary, with named or keyword arguments keeping the call site legible, is fine. Judge by whether grouping would actually cut what a caller has to track to call it correctly. The parameter count by itself proves nothing.

- **Output argument.** A function takes an argument and hands back its result by mutating that argument — the caller can't tell it's an output channel without reading the body. Fires when the diff adds or changes a function that writes into a parameter it received (pushes into a passed-in list, sets a field on a passed-in object) as its way of producing a result, where a return value would say the same thing. Flag, don't fix: route to `toby-swd-interfaces`. Moving the result from parameter to return value changes the signature and every caller. Exception: output parameters that are the idiom for the operation — Go's `(result, err)`, a documented caller-provided buffer for performance, or a method whose entire declared job is mutating the receiver it was called on. Ordinary state-changing behavior is not a smuggled result.

- **Flag / selector argument.** A boolean or enum parameter that tells a function which of two different behaviors to run, where the caller could pick between two plainly named functions instead. Fires when a changed or new function branches on a bool or enum parameter near the top of its body into substantially different code paths, and the parameter's only job is choosing which path runs. Flag, don't fix: route to `toby-swd-interfaces`. Splitting into two named functions, or consolidating into one with a clearer parameter, changes the public surface every caller sees. Exception: a parameter that selects among values of one coherent operation is fine — that's the case toby-swd-interfaces' own "one method per caller-shape" guidance argues for consolidating. Ask whether the parameter picks a value the operation acts on, or which operation runs. Only the second is this smell.

- **Message chain.** A caller reaches through several objects to get what it needs — `a.getB().getC().getD().getValue()` — coupling itself to the whole intermediate structure. Fires when a changed line chains three or more navigations through different objects' accessors to reach a final value or call. Flag, don't fix: route to `toby-swd-interfaces`. The fix is usually a new method on an intermediate object that does the reaching internally, which changes that object's interface. Exception: a fluent builder or a functional pipeline — `.map().filter().reduce()`, a query builder — where each call returns a new value of the same conceptual type, one hop at a time.

- **Primitive obsession.** A domain concept — money, a phone number, a date range, a role code — represented as a bare string, int, or float, with the same parsing or validation logic for that concept copied at each use site. Fires when a new field or parameter representing a recognizable domain concept is typed as a raw primitive, and the same parsing, validation, or formatting for that concept already appears at two or more other call sites — grep for it the same way this skill already greps for repo patterns. Flag, don't fix: route to `toby-swd-interfaces`. Introducing the dedicated type changes every call site that currently passes the raw primitive. Exception: a primitive used in exactly one place with no duplicated logic elsewhere — wrapping one unremarkable string in a type is speculative generality in reverse. Duplicated parsing or validation logic across sites is the tell; a bare type on its own is normal code.

- **Accessors as the public surface.** An interface that's mostly per-field get and set methods exposes the data layout with extra syntax — the same shape as the implementation, shallow by definition. Fires when a new or changed class's public methods are mostly getters and setters for its own fields, with no operation that names intent. Flag, don't fix: route to `toby-swd-interfaces`, which already carries this exact red flag. Replacing accessors with intent-named operations (`reserve`, `markPaid`) changes the public surface every caller uses. Exception: a record that exists deliberately as plain data, with the behavior over it owned by another module — there the data is the contract, and depth lives in the module that owns the behavior.

- **Speculative generality.** A parameter, config option, or extension point added for a future that hasn't arrived — generality with no named near-term caller. Fires when a new parameter or option has no current caller using anything but its default, and grepping for callers turns up no concretely named near-future use either. Flag, don't fix: route to `toby-swd-interfaces`, which already carries this exact check. Removing an unused option is a signature change, and deciding whether the generality earns its keep is an interface-design call. Exception: an interface covering today's needs plus one or two named near-future variants. The line is whether a real use can be named.

### Route to toby-swd-modules

- **Artificial coupling.** A constant, utility function, or type dropped inside a class or module it has no real relationship to, because that's where it was needed first. Fires when the diff adds a general-purpose constant or helper inside a specific, unrelated class, and nothing about that class's own job explains why it owns this. Flag, don't fix: route to `toby-swd-modules`. Moving it to where it belongs is a decision about which module owns it. Exception: the two things share real knowledge (passes the decompose-by-knowledge test), or the placement follows an established repo convention — every constant for a domain deliberately living in that domain's file, even with one call site elsewhere.

- **Feature envy.** A method that reads and calls another object's data more than its own — doing that object's job from the wrong side of the boundary. Fires when a changed method's body is mostly a chain of getters and fields pulled from one other object, with little use of its own class's state, and that other object could reasonably own the operation. Flag, don't fix: route to `toby-swd-modules`. Moving the method changes which class owns the operation and every caller of both classes. Exception: a method whose entire declared job is combining or comparing data across objects — a comparator, mapper, reducer, or aggregator reads several objects by design.

- **Divergent change.** One class or module edited for more than one unrelated reason in the same change — a sign it's carrying more than one piece of knowledge. Fires when the diff's stated intent is one change, but the edits inside a single file or class serve visibly unrelated purposes — a pricing-rule tweak and a display-copy tweak landing in the same class in the same diff. Judge this off the diff in front of you; a file's commit history is a full-file read this skill doesn't do. Flag, don't fix: route to `toby-swd-modules`. Splitting the class by responsibility is a module redesign. Exception: a class with one cohesive responsibility that legitimately needs many small methods — a serializer with one method per field type. Unrelated reasons behind the edits are the tell; method count alone says nothing.

- **Shotgun surgery.** A single conceptual change forces small edits scattered across many files — the mirror of divergent change, and the diff-visible symptom of information leakage. Fires when the diff touches many files with small, similar-shaped edits — a field added to N structs, a case added to N switch statements — that all encode the same underlying decision. Flag, don't fix: route to `toby-swd-modules`. Consolidating the scattered decision into one owner is a module redesign. Exception: the N edits are independent facts that happen to land together — a changelog entry, a version bump, and a config update in one diff are unrelated bookkeeping. The tell is that all N edits encode the same knowledge — change it again and all N change again the same way.

- **Shallow module.** The interface costs almost as much to learn as the implementation would cost to just inline at the call site. Fires when a new or changed module's public surface — parameters, methods, required setup — takes about as much explaining as its internals would. Flag, don't fix: route to `toby-swd-modules`, which already carries this check under Depth check. Fixing it means redesigning the module's boundary. Exception: some small utilities are unavoidably shallow. Don't inflate a trivial helper into artificial depth to dodge the label.

- **Information leakage.** One hidden design decision — a file format, a wire protocol, a storage layout, a policy — reflected in more than one module, so changing the decision means changing all of them. Fires when the diff touches two or more modules to express what is really one decision. Flag, don't fix: route to `toby-swd-modules`, which already carries this check. Moving the decision so it lives in exactly one module is a change across files. Exception: a dispatcher and the handlers it selects between, several implementations of one interface, a decorator and the object it wraps, or an interface known to both caller and implementer — each contributes distinct functionality despite the shared shape. Two blocks that share text while answering to different reasons to change are also fine, however identical they look. Ask what would make each one change; separate answers mean separate code.

- **Pass-through method.** A method that does almost nothing but forward its arguments to another method with a near-identical signature, adding no logic of its own. Fires when a new or changed method's body is a single call to another method, passing the same arguments through unchanged. Flag, don't fix: route to `toby-swd-modules`, which already carries this check. The fix — exposing the lower module directly, redistributing responsibility, or merging the two — is a boundary decision. Exception: a layer that needs a stable entry point about to carry real logic — name the concrete near-future need, or the pass-through stands as the smell it looks like. Implementing a shared interface doesn't excuse it by itself: toby-swd-modules calls a decorator that adds little a shallow pass-through in disguise, worth questioning even when it satisfies a contract.

## Not on this list, on purpose

**Refused bequest** (a subclass that uses only a slice of what it inherits) doesn't get an entry. Its diff-visible half — a subclass overriding an inherited method to throw or no-op — is already `toby-swd-modules`' "Deep implementation-inheritance hierarchy" red flag. The rest of the definition needs a full census of the parent class's public methods against everything the subclass actually calls, which means opening and reading an unrelated file end to end. That's a full-file read this skill doesn't do during a cleanup pass — flag the override half under the existing red flag and stop there.

A numeric ceiling on function length, "comments are always failures," a blanket "duplication is evil," and a TDD-mandates-test-first rule are also absent, deliberately. Each one contradicts a position `toby-swd-modules`, `toby-swd-clarity`, or `toby-swd-interfaces` already states for this repo — depth over line count, comments as the legitimate carrier of what code can't say, knowledge-gated duplication, interface-first design. Adding any of them here would put this skill at odds with the skills that wrote the code in the first place.
