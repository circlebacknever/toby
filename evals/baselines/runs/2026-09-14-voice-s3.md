## 2
A retry around the whole sync job would write duplicate rows, because the job is not idempotent. A run that fails partway has already written some rows, and the retry writes those rows again. So two failures a week become two batches of duplicate rows a week, and duplicates are harder to find than a failed job.

If you want a retry this week, wrap only the step that fails, and only if that step writes nothing before it errors. Otherwise the writes need to become upserts keyed on whatever identifies a source row, and then a retry of the whole job is safe. Do you have the error output from either of the last two failures?

## 3
This PR moves the rate-limit checks from four route handlers into one middleware.

### Behavior change
The limit now applies per account across all routes. Before this PR, each route kept a separate bucket per account, so an account could use its full limit on all four routes. An account that calls several of those routes will now get a 429 sooner. Before merging, check whether any client depends on the old per-route limit, and raise the limit value if one does.

### Changes
- Adds a middleware that runs the rate-limit check for the four routes.
- Deletes the token-bucket code that each of the four handlers had its own copy of.
- Adds a test for the 429 response, which had no test before this PR.
