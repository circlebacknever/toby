## 1
The flaky test asserts on a timestamp formatted in the machine's local timezone, and CI runs in UTC. That timezone mismatch is why the test passes locally every time and fails on CI about one run in nine. I have not checked why the mismatch breaks only some CI runs. The test is not fixed yet. Next I will format the timestamp in UTC inside the test, then rerun the CI job ten times.

## 2
A retry wrapper around the whole sync job will write duplicate rows, because the job is not idempotent. When a run fails partway, the rows it already wrote stay in the table, and the retry writes them again. So about twice a week the job would leave duplicate rows in the table, and those are harder to find than a failed run. The fix is to run the job's writes in one transaction, so a failed run leaves no rows behind. If the job writes too much for one transaction, add a unique key on those rows and change the inserts to upserts. After either change, the retry wrapper is safe to add.

## 3
Move rate-limit checks into one middleware

Rate-limit checks now run in one middleware. The four route handlers no longer check the limit themselves, and this PR deletes the token-bucket code that each handler had a copy of.

The limit now applies to each account across all four routes. Before this PR, each route kept its own bucket for each account, so an account could use its full limit on every route. An account that spreads requests across those routes now shares one bucket, so it can reach a 429 sooner. Before merging, ask the owners of clients that call these routes whether they depend on the per-route limits.

A new test covers the 429 response, which had no test before.
