## 2
A retry wrapper around the whole sync job will write duplicate rows. When a run fails partway, the rows it already wrote stay in the table, and the retry writes them a second time. At your estimate of two failures a week, that means two batches of duplicates to find and delete by hand. You can make a retry safe without finding the cause of the failures. If the job writes all its rows inside one database transaction, a failed run leaves no rows behind. If the job instead inserts on a unique key and skips rows that already exist, a second write of the same row changes nothing. Once one of those is in, I can add the retry wrapper. Which one fits the sync job's writes?

## 3
This PR moves the rate-limit checks out of four route handlers and into one middleware. Each of the four handlers had its own copy of the token-bucket code, and this PR deletes those copies.

One behavior changes. Before this PR, each route kept a separate limit for each account, so an account could use its full limit on every route. The middleware now keeps one limit per account across all four routes. As a result, a client that spreads requests across the four routes will get a 429 response sooner. Before merging, check whether any client depends on a separate limit per route.

The PR also adds a test for the 429 path, which had no test before. The test sends requests past the limit and checks that the response status is 429.
