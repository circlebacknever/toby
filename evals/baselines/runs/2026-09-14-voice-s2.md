## 2
A retry around the whole sync job will write duplicate rows, because the job is not idempotent. When a run fails partway, the rows it already wrote stay in the table, and the retry writes them a second time. Each of the two weekly failures would then leave duplicate data, which is harder to find than a failed job. The smaller fix is to make a second run safe first. If the job writes with an upsert on a unique key, the retry overwrites the rows from the failed run. After that change, the wrapper is safe to add. I have not read the write code, so I cannot say how large that change is. Which tables does the sync job write to?

## 3
This PR moves the rate-limit checks from four route handlers into one middleware.

### Changes
- The four route handlers now call the rate-limit middleware and contain no rate-limit code.
- This PR deletes the duplicated token-bucket code from those handlers, so the middleware has the only copy.
- A new test sends requests past the limit and asserts that the response is 429. No test covered the 429 path before this PR.

### Behavior change
The limit now applies once per account across all routes. Before this PR, each route kept a separate limit for each account. An account could use the full limit on each of the four routes. After this PR, requests to all four routes count against one limit, so clients that call several routes will get 429 responses sooner.
